Why is this an issue?

Variable shadowing happens when a variable declared in a specific scope has the same name as a variable in an outer scope.

This can lead to three main problems:

  • Confusion: the same name can refer to different variables in different parts of the scope, making the code harder to read and understand.
  • Unintended behavior: you might accidentally use the wrong variable, leading to hard-to-detect bugs.
  • Maintenance issues: if the inner variable is removed or renamed, the code's behavior may change unexpectedly because the outer variable is now being used.

To avoid these problems, rename the shadowing variable, the shadowed variable, or both so that each identifier is unique and meaningful.

Noncompliant code example

void f(int x, bool b) {
  int y = 4;
  if (b) {
    int x = 7; // Noncompliant: the parameter "x" is shadowed.
    int y = 9; // Noncompliant: the local variable "y" is shadowed.
  }
}

Compliant solution

void f(int x, bool b) {
  int y = 4;
  if (b) {
    int innerX = 7;
    int innerY = 9;
  }
}

Exceptions

Variables used in a member initializer list are not reported by this rule because shadowing in that context is a common and intentional pattern.

Caveats

Variables introduced in the condition of an if statement can remain in scope for the optional else branch. This can make shadowing harder to spot, especially in else if chains.

This rule also reports some cases where an identifier is inaccessible according to the strict language rules, because the resulting code is still confusing and fragile.

Resources

External coding guidelines

  • MISRA C:2004, 5.2 - Identifiers in an inner scope shall not use the same name as an identifier in an outer scope, and therefore hide that identifier
  • MISRA C++:2008, 2-10-2 - Identifiers declared in an inner scope shall not hide an identifier declared in an outer scope
  • MISRA C:2012, 5.3 - An identifier declared in an inner scope shall not hide an identifier declared in an outer scope

Standards

  • CERT - DCL01-C. Do not reuse variable names in subscopes
